Evals are not tests

19 July 2026 · 9 min · Method

The first eval harness I built was really a test suite wearing a costume. It asserted. It went green or it went red, and when it went red I fixed the thing it pointed at, and I felt productive in the way you feel productive when you are moving quickly in a direction nobody has checked.

A test asks a closed question: did this function return what I said it would? An eval asks an open one: is this system still behaving the way it did last week, on inputs I have not thought of yet? The second question has no green.

A test fails. An eval drifts. You do not notice drift by watching for red.

What changed for me was tracking distributions instead of assertions. Not did the router pick correctly, but how confidently did it pick, across the whole set, compared to the last five runs. The failure mode I had been chasing for a month showed up immediately: the router had not gotten worse at choosing. It had gotten less certain about everything, uniformly, and the tie-breaking was doing the real work.
